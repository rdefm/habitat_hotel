Habitat Hotel — Chunk 1 Implementation Brief (Milestone M1: "The Afternoon")

Audience: a fresh Claude Code session with no prior context. This document is self-contained — read it fully before writing any code.

Engine: Godot 4.x, GDScript only (no C#). The exact version is pinned in Step 0 below. All code must target the Godot 4 API — never Godot 3 (no yield, no onready var without @, no KinematicBody2D; use await, @onready, CharacterBody2D, Callable signals, etc.). If unsure whether an API is 4.x, check the installed version's docs, not memory.

Part A — What You Are Building and Why

Habitat Hotel is a cozy, funny hotel-management sim about running a hotel for animals, for mobile (portrait), premium one-off purchase. The player's core verb: matching arriving guests to rooms by hand, under light (never stressful) time pressure.

Chunk 1 = Milestone M1: the core loop skeleton. A playable day cycle where guests check out in the morning, housekeeping races to turn rooms over, an arrival queue forms in the afternoon, and the player drags guests into rooms. Placeholder visuals, real feel.

The playtest question this chunk must answer: "Is seating guests fun for ten consecutive in-game days, with nothing else in the game?" Everything you build serves that question. Everything not needed for it is out of scope (Part H).

Design pillars (constrain every decision)
The player is the concierge, not the spreadsheet. Matching by hand is the game.
Pressure, never stress. Patience decays slowly; pause is always available; nothing punishes hard.
Flavor is signal. (Mostly later chunks — but even placeholder text should be dry, warm, specific.)
Setbacks are stories. No fail states. A guest walking away is a small miss, not a punishment.
The day (four phases, in-game "sim time")
Phase	What happens	Player's job
Morning	Guests whose stay ended check out → rooms flip dirty → housekeeping cleans them one at a time, in order.	Watch the race set up; build on empty plots.
Afternoon (main event)	The arrival queue forms at reception. Rooms cleaned in time are bookable; rooms still dirty can finish cleaning during the queue.	Drag guests to rooms. The whole game.
Evening	Stragglers; quiet wind-down.	Light touch.
Night	Instant interstitial: day summary screen, next day's arrivals generated, save.	Read summary, tap to start next day.

Pop-ins: small chance of an off-schedule arrival in morning or evening — a readiness check, not a rush.

The day's spine: checkouts happen hours (of sim time) before the afternoon rush. The tension is "will housekeeping turn the rooms in time?" Tune the balance numbers so that on a busy day, 1–2 rooms are still mid-clean when the queue forms.

The matching interaction (the heart — get this feel right)
Queued guests show: species icon (placeholder), party size, needs as tag chips, likes as fainter chips, and a patience face (3 states: content → huffy → leaving-soon).
Tap/press a queued guest → compatible rooms glow on the grid: gold = covers all needs and fits the party; amber = fits the party but misses ≥1 need. Incompatible rooms (too small for even a split remainder, occupied, dirty, locked) don't glow.
Drag guest → room to seat them. Dropping on an amber room shows a one-line confirm dialog naming the missing tag(s) ("The Lagoon Room isn't quiet…") with Seat / Cancel.
Party rules: if a party exceeds one room's capacity, the player may seat them across multiple rooms — after the first drop, the remaining members stay in the queue as a "remainder" chip and can be dragged to another room (flat satisfaction penalty per extra room used). The player may also seat only part of a party and let the remainder leave (partial seating — remainder walks, no penalty beyond the missed revenue; seated members get a small satisfaction nick).
Patience: decays in sim time (therefore identical difficulty at 1x and 2x). When it empties, the guest walks: logged as turned away, small grumpy exit, no other penalty. Species have patience multipliers (tortoise ≈ effectively infinite; pigeon short).
Pause is honorable: pressing a queued guest soft-slows sim time to 0.3x while held/selected; the pause button hard-stops it. Every menu auto-pauses.
What "fun" depends on (tuning intent)
A full queue must be comfortably clearable by an attentive player at 1x and 2x.
The interesting moments are: choosing amber vs. waiting for a clean to finish; splitting a big party; triaging when two impatient parties want the same room. The generator (Part E) must produce these situations regularly but not constantly.

Part C — Project Structure & Architecture (load-bearing for all future chunks)

    sim_state.gd          # the entire mutable game state (serializable)
    sim_clock.gd          # phases, day counter, sim-time
    sim_arrivals.gd       # nightly arrival-list generation + pop-ins (seeded RNG)
    sim_queue.gd          # queue entries, patience, walk-aways
    sim_rooms.gd          # room states (vacant/occupied/dirty/cleaning), housekeeping service
    sim_matching.gd       # fit evaluation (gold/amber/none), seating, party split
    sim_economy_stub.gd   # placeholder cash + per-stay satisfaction record (real economy = M3)
    sim_events.gd         # event definitions + queue (sim → presentation)
    sim_save.gd           # versioned JSON serialize/deserialize of sim_state
  game/                   # Presentation. Nodes/scenes. Consumes sim events, sends commands.
    main.tscn / main.gd
    grid/                 # hotel grid view, room tiles, glow states
    queue/                # queue strip, guest chips, patience faces
    hud/                  # top bar, speed controls, pause
    build/                # build menu (minimal)
    summary/              # night summary screen
    stubs/sprite_factory.gd  # ALL visuals created here (see Part G)
  tests/
    run_tests.gd          # headless entry point
    test_*.gd             # one file per area

The prime architectural rule: sim/ never touches game/, and game/ never mutates sim state directly.

Commands in: the UI calls SimGame.submit(command) with typed command dictionaries, e.g. {type="seat_guest", guest_id, room_id, party_count}, {type="build_room", plot_id, room_type}, {type="set_speed", value}. The sim validates every command (never trust the UI) and rejects invalid ones with a result the UI can surface.
Events out: the sim appends typed events to an outbox each tick, e.g. guest_arrived, guest_seated, guest_walked, room_state_changed, phase_changed, day_summary_ready, clean_finished. Presentation drains the outbox each frame and animates accordingly. Presentation may read sim state for display but never writes it.
Fixed timestep: sim advances at 8 ticks per sim-second; presentation interpolates. Game speed (pause/1x/2x/soft-slow) scales how much sim-time elapses per real frame — inside the clock, so all sim logic is speed-agnostic.
Determinism: one seeded RNG owned by the sim (sim_state.rng_seed + call counter or state serialized). Same seed + same command sequence ⇒ identical outcomes. This is a test invariant, not a nice-to-have.
Save: sim_save.gd writes {schema_version: 1, ...state} as JSON to user://save.json at each Night phase. Loading a higher schema_version than known fails gracefully. Every future chunk migrates the schema forward; that's why it exists now.

Why this matters for future chunks: M2 adds staff as new sim systems + new commands; M3 attaches economy/reviews to events you're already emitting; M5 adds seasons to a clock that already has the field. If sim and presentation stay cleanly split, every future chunk is additive.

Part E — Simulation Rules (precise)

Clock. Sim-time flows through morning → afternoon → evening at the configured lengths, then Night (no duration — sim halts, emits day_summary_ready, and waits for a {type="next_day"} command). Day counter starts at 1. A season field exists in state (always "summer" in M1) so the schema is future-proof.

Nightly generation. At Night, generate tomorrow's arrival list (seeded RNG): draw N parties (per arrivals_ramp_by_day), each with species (weighted, tier-filtered), party size, and stay length (uniform in species range). Assign each party an arrival offset within the afternoon phase (spread across the first 70% of it). Independently roll pop-ins for morning/evening. Store the full list in state — future chunks will read this for the Trumpet forecast, so it must exist as data the night before, even though M1 shows the player nothing.

Checkout. At Morning start, every occupied room whose stay is complete checks out simultaneously: emit guest_checked_out (with the stay's final satisfaction), credit cash = nightly_rate × nights × party members in that room (placeholder economy), flip room to dirty, append it to the housekeeping order.

Housekeeping. One abstract housekeeping service (staff arrive in M2): cleans dirty rooms strictly one at a time, in the order they became dirty, clean_duration_sim_seconds each, running through morning/afternoon/evening. Emits clean_started / clean_finished. A room becomes seatable the moment cleaning finishes — including mid-queue. (Design intent: with 3–4 checkouts, the last room finishes partway into the afternoon. Verify with the pacing test.)

Queue & patience. Arriving parties append to the queue and emit guest_arrived. Patience = base_patience_sim_seconds × species.patience_mult, decays only while in the queue, paused while the player is press-holding that guest (soft-slow also applies globally). At 0: emit guest_walked with reason "impatient", log to the turn-away record (data for future chunks), remove. If a party can't fit anywhere at all it still just waits out its patience — no special case.

Fit evaluation (sim_matching.gd, single authoritative function — the UI's glow colors come from asking the sim, never from UI-side logic):

GOLD: room vacant+clean, capacity ≥ party count being placed, room tags ⊇ species needs.
AMBER: room vacant+clean, capacity ≥ party count being placed, ≥1 need missing.
NONE: otherwise (occupied, dirty, cleaning, capacity 0 remaining… ).

Seating & satisfaction. On a valid seat_guest command: occupy the room (or partially — see party rules in Part A), start the stay clock (stays are measured in nights; a guest seated on day D with stay S checks out on morning of day D+S). Record a per-stay satisfaction value at seating time: satisfaction_base + per_like_met×likes_met − amber_penalty×needs_missing − split/partial penalties, clamped to [0, cap]. Store it on the stay; report it at checkout and in the day summary. (Reviews/Hearts/reputation consume this in M3 — the number just needs to exist and be right.)

Build. build_room on an empty plot: validate cash and tier, deduct, place instantly, emit room_built. No build menu forecast section in M1 (the Trumpet replaces it in M3).

Day summary (Night screen). Show: day number, cash delta, guests seated / walked (with reasons), perfect fits vs. amber seats, occupancy %, mean satisfaction of today's checkouts, and rooms cleaned. Plain, readable, one screen. Then a single button: "Open tomorrow."

Part F — Headless Test Harness (required, not optional)

Run via: godot --headless --script res://tests/run_tests.gd (exit code 0 on pass, non-zero with readable failure output). Because sim/ is pure RefCounted, tests construct SimGame directly and drive it with synthetic commands and advance(dt) calls — no scene tree needed.

Minimum test suite:

Determinism: same seed + same scripted command sequence for 10 days ⇒ byte-identical serialized final state.
Save/load roundtrip: save at night of day 3, load into a fresh SimGame, run both originals and loaded copies 3 more days with the same commands ⇒ identical state.
Fit function truth table: every species × every room ⇒ assert expected GOLD/AMBER/NONE (this doubles as a design-data regression test — e.g. flamingo×veranda_suite must be GOLD).
Party split math: a 6-pigeon party across two rooms produces correct occupancy and correct satisfaction penalties; partial seating produces a walked remainder with no extra penalties.
Cleaning race pacing: with 4 morning checkouts, assert the last clean_finished lands inside the afternoon phase (the intended tension), not before it starts and not after it ends.
Queue clearability: an "attentive bot" policy (always seats the best available option the moment it exists) clears a max-arrivals day with zero impatient walk-aways at 1x — and, because patience is sim-time, the same test at 2x is definitionally identical (assert it anyway).
No-space day: more arrivals than capacity ⇒ excess walk with reason logged, sim never errors, day completes.
Ten-day soak: bot plays 10 days on 5 different seeds ⇒ no crashes, cash never NaN, all invariants hold (no room simultaneously dirty+occupied, queue empty at day end, etc.).

Tests 5 and 6 are the balance instruments — when tuning balance.json, these tell you whether the day still works before you ever open the editor.

Part G — Presentation Layer (placeholder visuals, real feel)

Viewport: portrait. Base logical resolution 540×960, canvas_items stretch mode, expand aspect, nearest-neighbor default texture filter (pixel-art-ready). Desktop dev window is fine; input must be written touch-compatible (all interactions = press / drag / release; no hover-dependent or right-click behavior).

Layout (top to bottom): HUD bar (cash, day, phase name, phase-progress bar, pause/1x/2x) → queue strip (horizontally scrollable guest chips) → hotel grid (3 floors × 4 plots, the largest region) → bottom strip (context line + button to reopen last day summary).

The SpriteFactory rule: every visual entity (guest chip, room tile, tag chip, patience face) is created through game/stubs/sprite_factory.gd, which currently returns programmer-art nodes: ColorRect + Label compositions (species = colored rounded rect + 2-letter code; tags = small labeled chips; patience = colored dot: green/amber/red). No emoji, no downloaded assets, no drawing outside the factory. When real pixel art arrives in a later chunk, only this file changes.

Interaction feel (spend real effort here — this is the product):

Press a guest chip → it lifts slightly, compatible rooms glow (gold/amber borders + slight brightness), sim soft-slows.
Drag → a ghost of the chip follows the finger; the currently-hovered room highlights stronger; invalid rooms give a tiny "nudge away" shake if dropped on.
Drop on gold → satisfying snap animation into the tile, small scale-pop, queue chip departs. Drop on amber → confirm dialog (auto-pauses), then the same snap.
Room tiles show: room name, tag chips, occupancy pips (filled per guest), and state tint (vacant / occupied / dirty with a small broom icon placeholder / mid-clean with a progress sliver).
Cleaning finishing mid-queue should be noticeable: the tile does a small "fresh" flash so the player catches the moment a gamble pays off.
Every menu (build, summary, amber confirm) pauses the sim; closing resumes prior speed.

Build menu: tap empty plot → simple list of available rooms (name, tag chips, capacity, cost; grayed if unaffordable) → tap to build. Instant, no confirm beyond the tap.
