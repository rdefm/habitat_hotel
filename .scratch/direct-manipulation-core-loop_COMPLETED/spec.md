# Direct-manipulation core loop: Floors, manual seating, Stations, and the Terrace

## Problem Statement

`hotel_habitat_plan.md`'s original design and the game as currently built in Godot both use a menu-driven, auto-resolved core loop: guests are placed into rooms automatically by `Matcher.decide()` under a global `Policy` toggle (Perfect Fit Only / Fill Vacancies), the hotel is a flat 18-slot grid where any room type can go in any slot, and Staff/Hire are unimplemented stubs with no Dining loop at all.

A later reconciliation against a working HTML/JS prototype (`habitat-hotel-prototype-4.html`) produced five accepted ADRs that replace this with a direct-manipulation model instead. Two of those ADRs (0001, 0004) describe player-facing behavior that directly contradicts what's actually implemented today — `sim/matcher.gd`, `ui/policy_menu.gd`, and `data/slot_layout.json` all still encode the superseded design, and ADR-0001 explicitly calls out that it "supersedes... the Policy menu described in §13/GUIDE.md §10." Two more (0002/0005, minimal slice) and one more (0003) describe an entire Dining pillar and Staffer/Station system that don't exist in the Godot build at all yet.

Left alone, the game continues to ship a core loop the project's own accepted decisions say is wrong, and the player-facing guide (`GUIDE.md`) documents behavior (§9 seating, §10 Policy) that's already flagged for replacement.

## Solution

Rebuild the core loop directly on the accepted ADRs, using `habitat-hotel-prototype-4.html` as the behavioral reference (not visual, not architectural — Godot's data-driven JSON + sim/presentation split still governs):

1. **Floors, not a flat slot grid** (ADR-0004): each Room type owns one Floor, capped at a fixed instance count, with an open Build Slot at the end of the row once under the cap.
2. **Manual seating, no auto-matcher, no Policy menu** (ADR-0001): arriving Parties wait at Reception with a decaying Patience timer; the player taps a Party then taps a Room to seat it, with a green/amber Match hint (green = every Need met, amber = seatable but missing a Need, requires a confirmation), or lets Patience run out and the Party walks away.
3. **A minimal Roster with per-Station Skill** (ADR-0002/0005, minimal slice only): the three authored starters (Biscuit, Marlon, Shelly) each carry a Skill (1-5) rating at every Station (Reception, Bellhop, Housekeeping, Kitchen), freely reassignable by tapping a Staffer then a Station. Training, traits, and further Roster unlocks are explicitly deferred.
4. **The Terrace as a core pillar** (ADR-0003): present and operating from day one (never built or star-gated), running breakfast (every current room guest, once each morning) and walk-in Dinner service (a Patience-driven arrival queue, evening only) gated on Kitchen Station skill, with a player-chosen Daily Special biasing which Species show up as Walk-in Diners. Critically, this spec also applies the fix ADR-0003 calls for that the reference prototype itself never made: dining outcomes (walk-in diners served, room guests' dinner add-on) feed Reputation and Hearts the same way a Checkout review does, not a cash-only side loop.

`GameState`/`SimController` remain the sim/presentation seam: all of the above is tested headlessly through their public API, with UI (grid, Reception, Terrace, Staff) as a thin layer that reads that state and calls it — no new seam is introduced.

## User Stories

1. As a player, I want each Floor to be dedicated to one Room type, so that I can read the building's layout as a stable elevation instead of a generic grid.
2. As a player, I want a Build Slot at the end of a Floor's row whenever that Floor is under its instance cap, so that "build another Cozy Nook" is a single tap on that Floor.
3. As a player, I want a Floor to stay hidden/locked until my Star level unlocks that Room type, so that the building's scope grows in step with my progression exactly as it does today.
4. As a player, I want tapping a Build Slot to open the same scoped room-catalog-for-this-spot flow that exists today (forecast, recently-turned-away, cash-permitting construction), so that building doesn't regress from its current UX.
5. As a player, I want tapping any already-built Room (on any Floor) to open its Upgrade menu, exactly as today, so that upgrade flows are unaffected by the Floor rework.
6. As a player, I want arriving Parties to show up in a visible, tappable queue at Reception rather than being resolved invisibly, so that seating becomes something I actually do rather than watch happen.
7. As a player, I want each waiting Party to show me their Species and party size at a glance, so that I can decide who to seat next without opening a detail screen.
8. As a player, I want a Party's wait growing "impatient," then "huffy" to be visible before they leave, so that I get a fair warning before losing a booking.
9. As a player, I want a Party who reaches the end of their Patience to walk away exactly as a turned-away guest does today (reputation impact split by reason: no eligible Room type, fully booked, or too expensive), so that the existing reputation/economy accounting isn't disrupted by the interaction change.
10. As a player, I want tapping a waiting Party then tapping a vacant Room to attempt seating them there, so that seating is a deliberate two-tap action on the world.
11. As a player, I want a Room that fully meets a selected Party's Needs to highlight green and seat them immediately on tap, so that a clear match doesn't need a confirmation step.
12. As a player, I want a Room that's missing one of the selected Party's Needs, but is still big enough, to highlight amber and ask me to confirm before seating (telling me what's missing), so that a mismatched stay is always my deliberate choice, never automatic.
13. As a player, I want a Room that's too small, already occupied, dirty, or unaffordable for the selected Party's budget tier to show no highlight at all and not respond to a tap, so that I can't accidentally attempt an invalid seating.
14. As a player, I want a Party larger than one Room's capacity to split across Rooms (seat part of the Party, the rest stays in the queue with its Patience preserved), so that big parties aren't an all-or-nothing booking.
15. As a player, I want the Policy menu removed entirely, so that the menu bar reflects that seating is no longer a global automated setting.
16. As a developer, I want `sim/matcher.gd`'s policy-branching logic (`strict_match`/`fill_vacancies`) removed rather than kept as a hidden fallback, so that there is exactly one seating code path to trust and test.
17. As a developer, I want the headless batch runner to seat every arrival through that same single seating path, driven by a simple scripted rule (prefer the smallest-capacity green match; else the smallest-capacity amber match; else leave it to expire), so that 60-day balancing runs still work unattended without a second seating implementation.
18. As a player, I want to see a small Roster of named Staffers (Biscuit, Marlon, Shelly), each with their own Skill rating at each of the four Stations, so that staffing feels like character-driven choices rather than an anonymous pool.
19. As a player, I want to tap a Staffer then tap a Station to assign or reassign them there, so that staffing follows the same direct-manipulation model as seating and building.
20. As a player, I want reassigning a Staffer who's mid-task to interrupt only that task (a half-cleaned Room reverts to dirty; an interrupted Kitchen job just returns its guest/diner to waiting) rather than losing other Staffers' progress, so that reassignment feels like a tactical lever, not a risky reset.
21. As a player, I want an empty Station (no Staffer assigned) to visibly degrade service — Reception empty means Patience burns faster, Bellhop empty means slower check-in, Housekeeping empty means rooms stay dirty longer, Kitchen empty means no breakfast or dinner service at all — so that leaving a Station uncovered has a clear, felt cost.
22. As a player, I want the Terrace to be present and usable from Day 1 without building or unlocking it, so that Dining feels like a core part of the hotel from the start, not a late-game amenity.
23. As a player, I want every currently-staying Party to join a breakfast queue each morning, served by whoever's on Kitchen duty, so that breakfast runs as a predictable daily beat.
24. As a player, I want walk-in Diners (visitors with no booked Room) to arrive at the Terrace during the evening on their own Patience timer, independent of the Room-booking Party queue, so that Dining has its own live-service rhythm.
25. As a player, I want to choose one Daily Special that biases which Species show up as Walk-in Diners that evening, so that I have a lever to actively shape dinner demand rather than just reacting to it.
26. As a player, I want a Kitchen Staffer's Skill to gate what they can serve (a low-Skill cook can run breakfast but can't keep up with dinner/walk-in service), so that Kitchen staffing is a genuine quality-vs-coverage tradeoff, not just a binary on/off.
27. As a player, I want a well-served Walk-in Diner or a room guest's dinner add-on to earn Hearts and move Reputation the same way a good Checkout review does, so that Dining feels load-bearing on my hotel's reputation, not a side cash trickle.
28. As a player, I want a poorly-served or unserved dining guest (huffy walk-in who leaves, or a room guest whose dinner never gets served) to cost Reputation the same way a bad stay or a lost walk-away does, so that neglecting the Terrace has the same stakes as neglecting Reception.
29. As a player, I want the Terrace to be eligible for purchasable/earnable upgrades the same way a Room is (rather than only Rooms having an upgrade path), so that investing Hearts/cash into Dining quality is possible.
30. As a developer, I want Dining's satisfaction/Hearts/Reputation math to reuse the same `Satisfaction` module patterns already used for Checkouts (rather than a second, parallel scoring system), so that tuning stays centralized in `data/balance.json`.
31. As a player, I want a room guest who opted into the dinner add-on at check-in to have that reflected on their Room card, so that I can tell at a glance which occupied Rooms also expect Kitchen service that evening.
32. As a developer, I want `GameState`/`SimController`'s public API (not Matcher, not any UI file) to remain the one seam every new system (Floors, seating, Stations, Dining) is tested against headlessly, so the existing sim/presentation split and batch-tooling story keep working without new test infrastructure per feature.

## Implementation Decisions

- **Floor data model**: `data/slot_layout.json` (flat, generic per-slot unlock table) is deleted. Each Room type's existing `unlock.star` field in `data/rooms.json` becomes its Floor's unlock condition directly; a new per-type `max_instances` field (reference value: 4) caps how many Build Slots that Floor can fill. `GameState.hotel_rooms` room instances are addressed by a stable per-instance identifier scoped to their Floor's `room_type_id` (e.g. an instance index within that type) rather than a single flat, globally-unique slot integer; every current consumer of the flat slot index (`HotelPanel`, `BuildMenu`, `UpgradeMenu`, `SimController`, EventBus signal payloads) is updated to this addressing scheme.
- **Seating replaces auto-matching entirely**: `sim/matcher.gd`'s `decide()` policy-branching (`strict_match`/`fill_vacancies`) and `GameState.matcher_policy` are removed. In their place:
  - A pure, side-effect-free **match-hint** function: given a Party's Species/Needs and a candidate Room's effective stats, returns `green` / `amber` / `none`.
  - A single mutating **seat action** on `SimController`'s public API (e.g. `seat_party(party_id, room_instance_id)`) that performs the actual admission — computing Satisfaction, updating cash/Hearts/Reputation bookkeeping, and emitting the existing EventBus lifecycle signals. Both the interactive UI (after a tap-Party, tap-Room pair) and the batch runner's scripted autopilot call this same function; there is no second admission path.
  - Arrivals become a visible, queryable **pending queue** (not resolved instantly within one Midday call as today): each entry carries a Patience value that decays tick-by-tick during Midday, mirroring the reference prototype's `waitTime`/`patience` fields, with the existing three walk-away reasons (`no_match_available`, `fully_booked`, `too_expensive`) computed at expiry using the same affordability/tag-coverage checks `Matcher` used to perform.
  - `ui/policy_menu.gd` is deleted; the main-screen menu bar drops its "Policy" entry.
- **Batch runner**: `sim/batch_runner.gd` keeps driving `Clock.force_advance_day()` unchanged (it already ticks day-by-day synchronously, so Patience decay works headlessly with no new "instant mode"), but its arrival-handling now calls the same `seat_party` action as interactive play, choosing a room for each pending arrival via a simple greedy rule (smallest-capacity green match; else smallest-capacity amber match; else leave to expire) rather than a policy parameter. The `policy` argument to `BatchRunner.run()` is removed.
- **Roster/Station minimal slice**: three authored Staffers (Biscuit, Marlon, Shelly — matching the reference prototype's names/home specialties) each get a `skills: {reception, bellhop, housekeeping, kitchen}` rating (1-5). Stations hold a list of assigned Staffer ids (not a 1:1 slot); reassignment moves a Staffer between Station lists and interrupts only that Staffer's in-flight job (a Housekeeping job reverts its Room to dirty; a Kitchen job returns its guest/diner entry to waiting — never removed from its queue, so nothing needs re-insertion). No hiring, firing, training, traits, or weekly candidate pool — that's explicitly out of scope (see below).
- **Terrace/Dining loop**: the Terrace is a fixed structure (like Reception), never built or unlocked, but carries an `upgrades` list the same shape as a Room's. Breakfast populates once each Morning phase from every currently-occupied Room's first occupant; walk-in Dinner arrivals spawn on a randomized interval during Evening, each with their own Patience queue independent of the Room-booking arrivals queue. A Kitchen Station Staffer serves whichever queue (breakfast or dinner) has a waiting entry, gated by a minimum Skill threshold for dinner/walk-in specifically (a low-Skill cook can clear breakfast but never picks up dinner/walk-in jobs) — mirroring `BREAKFAST_MIN_SKILL`/`DINNER_MIN_SKILL` in the reference prototype.
- **Dining feeds Reputation/Hearts (the ADR-0003 fix)**: a served Walk-in Diner or dinner add-on computes a Satisfaction-like score (Daily Special match = bonus, service speed by Skill) through the same `Satisfaction`/`balance.json`-driven module Checkouts already use, and that score drives Hearts and Reputation deltas exactly as a Checkout review does. A walk-away from the dinner queue (Patience expired) costs Reputation the same way a lost Party walk-away does. This is new behavior relative to both the current Godot build (no Dining at all) and the reference prototype (which is cash-only) — it is the specific correction ADR-0003 calls for.
- **Construction stays instant**: unlike the reference prototype's one-day build delay, Room construction remains immediate on confirming a Build Slot purchase, matching the current Godot behavior. ADR-0004 only locks in the Floor structure, not build timing, so this isn't silently changed as a side effect of the rework.
- **EventBus/naming**: guest lifecycle signals (`guest_seated`, `guest_turned_away`, `guest_checked_out`, etc.) may be renamed to use the `Party`/`Match` vocabulary from `CONTEXT.md` where it's a natural fit for the new signals this work adds (pending-arrival queued, Patience-tier changed, dining-guest served/walked-away) — existing signal names for behavior that isn't otherwise touched by this spec are not renamed just for consistency's sake.

## Testing Decisions

- Tests target the `GameState`/`SimController` public API headlessly (no UI, no Godot scene tree beyond what autoloads require) — this is the one seam for all four systems in this spec, consistent with the existing `sim`/presentation split and the project's stated GUT-testing intent in `hotel_habitat_plan.md` §6.
- Good tests here assert observable outcomes only: resulting `GameState` fields (cash, Hearts, Reputation, room occupancy, Roster/Station assignment) and emitted EventBus signals — never internal function call counts or private helper behavior.
- Coverage should include: Floor instance-cap enforcement and unlock-by-star gating; the match-hint function's green/amber/none classification across Need-coverage, capacity, and affordability edge cases; Patience decay and expiry producing the correct walk-away reason; Party-splits-across-rooms for oversized parties; Station reassignment correctly interrupting only the moved Staffer's in-flight job; Kitchen Skill gating breakfast-only vs. breakfast-and-dinner capability; a served Dining guest producing the same class of Hearts/Reputation deltas a Checkout review does; and a full headless multi-day batch run (via the reworked `BatchRunner`) completing without any guest/Party stuck in an unresolvable state.
- No test files currently exist in this repo (GUT is referenced in the plan but never wired up) — setting up the test framework itself is a prerequisite this spec's implementation will need to handle, not an existing seam to reuse.

## Out of Scope

- Staff training, traits, weekly hire-pool refresh, hiring, and firing (remainder of ADR-0002/0005 and Chunk 4) — the Roster in this spec is fixed at the three authored starters with Station reassignment only.
- Further Roster unlocks via star level/cash/story milestones — out of scope until training/traits exist to make a larger Roster meaningful.
- Seasons, offers, and incidents (Chunk 5) — untouched by this spec.
- Rewriting `GUIDE.md` itself — this spec changes the behavior GUIDE.md §9/§10/§13/§14 describe, but updating the player-facing guide's prose is a separate follow-up, not part of this implementation.
- Amenities (Pool, Sauna, Perch Garden) — unaffected by ADR-0003 and not touched here; they remain separate buildable slot-occupants exactly as today.
- Changing Room construction to a multi-day build delay — explicitly decided against above, kept instant.
- Any rebalancing of `data/balance.json` numbers for the new Dining Hearts/Reputation feed — initial values should be illustrative/wired-correctly, not tuned; tuning is a follow-up batch-runner exercise once this ships.

## Further Notes

- ADR-0001, ADR-0002, ADR-0003, ADR-0004, and ADR-0005 in `docs/adr/` are the authoritative decisions this spec implements; where this document and an ADR ever seem to disagree, the ADR wins and this spec has a bug.
- `habitat-hotel-prototype-4.html` is the structural/behavioral reference throughout (interaction flow, queue/Patience mechanics, Station gating) but is explicitly not a source of visual design, file layout, or the JSON-data-driven architecture — those remain governed by `CLAUDE.md`/`hotel_habitat_plan.md`.
- The reference prototype's room roster (`cozyNook`/`roostLoft`/`lagoonRoom`/`verandaSuite`/`iceGrotto`) and species roster (5 species, tiers 1-2 only) are a trimmed illustrative slice; this spec continues to use the full v1 roster already defined in `data/rooms.json`/`data/species.json` (6 room types, 8 species) — the prototype's smaller roster is not a scope signal.
- Once this ships, `GUIDE.md` §9 (seating), §10 (Policy — to be deleted), §13 (Staff), and §14 (Hire) will all be stale and should be revisited; flagged here so it isn't lost, but intentionally left out of this spec's scope.
