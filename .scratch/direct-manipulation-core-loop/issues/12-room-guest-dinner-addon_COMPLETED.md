# 12 — Room-guest dinner add-on

**What to build:** At check-in (seating), a Party can opt into a dinner add-on for their stay. An occupied Room whose guest opted in shows that on its Room card, so the player can tell at a glance which occupied Rooms also expect Kitchen service that evening. The add-on feeds the same dinner queue and scoring as a Walk-in Diner.

**Blocked by:** 04, 10

**Status:** done

- [x] A Party can opt into a dinner add-on as part of being seated
- [x] An occupied Room's card visibly indicates when its guest has an active dinner add-on
- [x] A room guest's dinner add-on joins the same Evening dinner queue and Kitchen-skill gating as Walk-in Diners
- [x] The add-on's outcome (served or not) feeds Reputation/Hearts per ticket 11

## Comments

`Sim.seat_party(party_id, room_type_id, instance_id, dinner_addon: bool = false)` gained the opt-in param (default `false`, so every existing caller/test is unaffected); `_admit_guest()` threads it onto the new guest record field `dinner_addon` and the room instance field `occupant_dinner_addon` (`GameState._new_room_instance()`'s new default-`false` field, reset alongside the other `occupant_*` fields on checkout). The choice is made once, at seating time -- there's no per-night re-offer.

`Sim._populate_walkin_queue()` (ticket 10) now also calls `_queue_room_guest_addons()`, which folds every currently-staying guest with `dinner_addon == true` into the same `walkin_queue` alongside that Evening's true Walk-in Diners -- identical entry shape (`id`, `name`, `species_id`, `party_size`, `patience`) plus a `guest_id` back-reference (`-1` on a true Walk-in Diner) so the entry can be traced back to its guest/Room. Because it's the same array feeding `_tick_dinner()`, the add-on automatically gets Walk-in Diners' exact Kitchen-skill gating (`stations.kitchen.dinner_min_skill`) and Patience decay (`dining.walkin_patience.*`, including the unstaffed-Kitchen multiplier) for free -- no ticket-12-specific service logic exists.

`Sim._resolve_room_guest_addon(entry)` is called from both `_serve_walkin_diner()` (a successful serve) and `_decay_walkin_patience()`'s expiry branch (Patience ran out) -- either way it clears `dinner_addon` on the guest record and `occupant_dinner_addon` on the Room, so the Room card indicator (and the queue) reflect that this Evening's choice is now resolved, matching ticket 11's existing Hearts/Reputation scoring path with zero dining-specific code of its own (see ticket 11's addendum).

UI: `ReceptionPanel` gained a `dinner_addon_selected: bool` field and a checkbox ("Add dinner service for this stay") shown only while a Party is selected -- it resets to `false` whenever the selection changes (`_on_card_pressed()`/`clear_selection()`) so it can't leak from one Party's seating to the next. `main_screen._on_seat_attempted()` reads it at the moment of the seat attempt and threads it through both the immediate-green path (`Sim.seat_party(..., dinner_addon)`) and the amber path (`SeatConfirmMenu.dinner_addon`, honored on confirm). `hotel_panel.gd`'s occupied-cell rendering appends `" + Dinner"` to the occupant line and a tooltip note whenever `occupant_dinner_addon` is true.

New tests: `tests/test_room_guest_dinner_addon.gd` (extends `sim_test_base.gd`, following `test_walkin_dinner.gd`/`test_dining_reputation.gd`'s conventions) -- opting in flags the guest/Room card and opting out doesn't; Evening queues an opted-in guest's add-on (and skips one who never opted in); the shared `dinner_min_skill` gate applies (Shelly, below threshold, never claims it); a served add-on moves Hearts/Reputation and clears both flags; an unserved (Patience-expired) add-on costs `reputation_delta_walkaway` and clears both flags. Reputation-delta tests capture their `_before` baseline only *after* settling into Evening (same precedent as `test_dining_reputation.gd`), since Day 1's own unrelated arrivals resolve their own Room-booking walk-aways during Midday/Evening and would otherwise pollute an earlier baseline; tests isolating the add-on's own serve/expiry timing strip that Evening's RNG-drawn true Walk-in Diners (`_strip_true_walkins()`) so a single Kitchen Staffer's one-job-at-a-time throughput isn't at the mercy of how many Walk-ins happened to spawn that day.

Verified instead via a one-off headless `--script` smoke run (autoloads fetched via `root.get_node()`, one `process_frame` await) exercising all four checklist items directly through `Sim`/`GameState`/`Clock`, plus a separate parse-only load of every touched script (`ui/reception_panel.gd`, `ui/hotel_panel.gd`, `ui/seat_confirm_menu.gd`, `ui/main_screen.gd`, `autoload/sim_controller.gd`, `autoload/game_state.gd`) to catch syntax errors the UI-only changes wouldn't otherwise exercise headlessly. ### Post-review addendum

A two-axis `/code-review` pass came back clean on Spec (all four boxes verified correct against the real diff, not just this file's own claims) with one fix applied on Standards: `dinner_addon` was being written independently in two places (`guests[gid]["dinner_addon"]` and the mirrored `room["occupant_dinner_addon"]`) across three call sites, a drift risk if a fourth mutation site showed up later. Extracted `Sim._set_dinner_addon(gid, value)` as the single place that keeps both in sync; `_admit_guest()` and `_resolve_room_guest_addon()` now call it instead of writing both fields inline. Re-verified via the same smoke-script approach after the refactor.

Two items were flagged and have since been addressed:

1. **Split-Room opt-in.** A Party split across multiple Rooms used to lose its dinner add-on opt-in on the remaining chunk once `ReceptionPanel`'s checkbox reset to `false` after each partial seat. Fixed by making the opt-in Party-level rather than per-`seat_party()`-call: `seat_party(..., dinner_addon)` now sticks `true` onto the Party dict (`party["dinner_addon"]`) the first time it's passed, and every later `seat_party()` call for the same still-queued `party_id` honors it automatically even if the UI's checkbox comes back unchecked. `ReceptionPanel` also seeds its checkbox from `Sim.pending_party()`'s own `dinner_addon` field on selection, so re-selecting a partially-seated Party's remainder shows the opt-in as already checked rather than lying about it. New test: `test_dinner_addon_carries_across_a_split_partys_remaining_chunks`.

2. **"Dining Party" vocabulary gap.** `CONTEXT.md`'s Dining section gained a **Dining Party** glossary entry -- the term its own Patience entry already anticipated ("A queue entry's (Party, Walk-in Diner, or Dining Party) tolerance timer") but never defined. It names the Evening dinner-queue entry this ticket's `_queue_room_guest_addons()` produces, contrasted with a Walk-in Diner. Code identifiers (`dinner_addon`, `_queue_room_guest_addons`, etc.) were intentionally left unrenamed -- the ticket's own spec text says "dinner add-on" for the opt-in/action, and "Dining Party" now names the queue-entry noun it produces, so the two terms coexist rather than conflict.
