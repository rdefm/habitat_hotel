## Comments

The Roster only has three Staffers for four Stations (`data/staffers.json`), and `BatchRunner.run()`'s existing reset leaves Kitchen empty by default (`GameState.DEFAULT_STATION_ASSIGNMENTS`, matching interactive play's starting coverage) — so a default batch run would only ever queue-and-lose Dining guests, never serve one, which wouldn't actually prove the Dining loop cooperates with the rest of the system. `sim/batch_runner.gd`'s `run()` gained an optional fourth parameter, `station_assignments: Dictionary = {}` (staffer_id -> station_id), applied once right after the reset through `Sim.assign_staffer()` — ticket 07's existing single reassignment path, not a new one. Defaults to `{}`, so every existing caller (`main.gd`'s `--batch=N` CLI mode, `tests/test_batch_runner_autopilot.gd`) is unaffected. A caller that wants a run to actually exercise Dining passes e.g. `{"marlon": "kitchen"}` — Marlon's kitchen skill (3) is the only starting Staffer that clears `stations.kitchen.dinner_min_skill`, at the cost of leaving Bellhop unstaffed for that run (just a flat check-in delay, nothing that can strand a guest). An unknown staffer/station id in the override now `push_error`s instead of failing silently.

`BatchRunner.CSV_COLUMNS` gained `dining_served`, `dining_positive_reviews`, `dining_neutral_reviews`, `dining_negative_reviews`, `dining_walked_away` — these were already being tracked in `Sim`'s `_day_metrics`/`day_summary` since ticket 11, just not surfaced in the batch CSV the balancing workflow actually reads, so the run's output stayed "legacy room/guest metrics" only. No new data-producing logic was needed; Floors are already reflected via the existing `occupancy_rate`/`matched_strict`/`matched_mismatched` columns (Room addressing has been Floor-based since ticket 02).

New test file `tests/test_integration_multiday.gd` (extends `sim_test_base.gd`): a 60-day run with `{"marlon": "kitchen"}` asserts every day's reputation stays in its 0-100 meter, cash continuity holds day-to-day, Hearts never decreases, and both Checkouts and served Dining guests occur (`total_checkouts > 0`, `total_dining_served > 0`), with `Sim.pending_arrivals`/`Sim.walkin_queue` empty after the run (nothing left stranded); a second test confirms the written CSV's header actually carries the new Dining columns alongside the existing Checkout-driven Reputation/Hearts ones; a third test re-runs with no `station_assignments` override (Kitchen left empty, ticket 06's original default) and confirms it still completes cleanly with zero Dining guests served, characterizing that the "no second path" guarantee holds either way.

Verification note: as in tickets 09/10/11, this environment's vendored `Godot_v4.4-stable_win64_console.exe` (4.4) can't run the GUT suite against this project (`config/features` requires 4.7). Unlike those tickets, this one *could* be verified through the actual engine end-to-end, since `main.gd`'s real `--batch=N` CLI entry point (not a raw `--script` override, which fails to resolve autoload globals like `Rng` when a `class_name`-annotated script is `preload()`-ed before the engine finishes autoload registration) exercises the exact same `BatchRunner.run()` code path a real balancing session would use. Ran `--headless --batch=60 --seed=12345` twice — once against a temporarily-patched `main.gd` passing `{"marlon": "kitchen"}`, once unpatched (default coverage) — and inspected both written CSVs directly: the Kitchen-staffed run served 1-2 Dining guests every single evening across all 60 days with zero Dining walk-aways and zero engine errors; the default-coverage run served zero Dining guests across all 60 days (every Walk-in Diner queued and lost to Patience expiry instead), also with zero engine errors — both matching the new test file's assertions exactly. `main.gd`'s temporary patch was reverted (`git checkout -- main.gd`) before committing; it was verification-only, not a real feature.
